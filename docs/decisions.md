# Design Decisions

1. **CLI language**: **Swift** — shared codebase with native apps via MahoNotesKit Swift Package

2. **Native app**: **Universal app** (one Xcode project, macOS + iPadOS + iOS, shared SwiftUI code)

3. **Sync architecture**: **iCloud** is the default sync backend for the app, but the sync layer is designed as an abstract `SyncProvider` protocol. iCloud is the first (and initially only) implementation. The abstraction preserves room for future backends: Google Drive, Synology Drive, WebDAV, Dropbox, etc. **GitHub** is a separate, optional layer for version control, cross-Apple-ID bridging, and publishing — not a general sync backend.

4. **Git on iOS**: Git CLI is not needed on iOS. The app uses **GitHub REST API** for all GitHub operations (vault clone/pull/push, publishing). On iOS/iPadOS, users manage GitHub vaults through the app UI (Settings → Vaults → Add GitHub vault), which handles OAuth + REST API interactions. On macOS CLI, `git` is used directly.

5. **Publishing**: Static site generated by app, deployed to user's GitHub Pages or other static hosting. **GitHub Pages free-tier limitations**: free accounts require a **public** repo for Pages (private repo Pages requires Pro/Team/Enterprise); site size ≤ 1 GB; bandwidth ≤ 100 GB/month (soft); 10 builds/hour. Our design separates the vault repo (can be private) from the publishing repo (must be public for free users). Alternative hosting (Netlify, Cloudflare Pages, Vercel) should be supported in the future — they allow private repos on free tiers and have more generous limits.

6. **Vector search**: 100% on-device, user-selectable model per device (all-MiniLM-L6-v2 default → multilingual-e5-large pro), sqlite-vec for vector storage, `swift-embeddings` for embedding runtime. See #21 for NLEmbedding removal rationale.

7. **Ruby annotation syntax**: `{base|annotation}` → renders to HTML `<ruby>` (web) / `AttributedString` (native). Language-agnostic: works for Japanese furigana, Taiwanese Tâi-lô/POJ, Chinese Zhuyin/Pinyin, Korean readings, etc.

8. **Embedding model**: User-selectable per device; 3 tiers from all-MiniLM-L6-v2 (90MB, default) to multilingual-e5-large (2.2GB, pro). All models run via `swift-embeddings` (MLTensor). All tiers support 中英日韓 multilingual search. See #21.

9. **Domain**: `notes.pcca.dev`

10. **App Store**: App must work standalone without server dependency

11. **Publishing ownership**: User-owned — each user publishes to their own GitHub Pages, we don't host content

12. **Multi-vault**: Users can register multiple vaults — multiple iCloud vaults + unlimited GitHub-backed vaults (read-write or read-only). Enables community content (public repos as read-only reference vaults) and knowledge separation.

13. **Single config file per vault**: `maho.yaml` is the ONE config file per vault (vault metadata + collections + optional GitHub/site settings). Originally `collections.yaml` was separate to reduce merge conflicts, but one file = one source of truth = cleaner UX.

14. **Vault registry in iCloud**: Registry lives in iCloud container (`iCloud~com.pcca.mahonotes/config/vaults.yaml`), not `~/.maho/`, so it syncs across all Apple devices automatically. Uses type-based resolution (no absolute paths — each platform resolves paths at runtime). Device-specific config (auth tokens, cache) stays in `~/.maho/` (macOS) or Keychain (iOS).

15. **`mn init` as onboarding wizard**: First-run interactive setup (choose vault type, set author, optional GitHub). After init, all vault management via `mn vault add/remove/list`. Supports non-interactive mode (`--icloud`, `--path`) for scripting.

16. **`--import` for non-Maho repos**: `mn vault add --import` auto-generates `maho.yaml` from a repo's directory structure (scanning `.md` files into collections). Generated config stored locally, not pushed to the source repo.

17. **Auto-detection on `mn vault add --github`**: When adding a GitHub vault, the CLI auto-detects two things via GitHub REST API: (a) **access level** — checks `permissions.push` on the repo; no push → auto-readonly, push → auto-readwrite; (b) **vault format** — checks if `maho.yaml` exists in repo root; present → native Maho vault, absent → auto-import (generate `maho.yaml` from directory structure). The `--readonly`, `--readwrite`, and `--import` flags become overrides that skip auto-detection. This simplifies the default UX to just `mn vault add <name> --github <repo>`.

18. **SyncProvider abstract protocol**: The sync layer is designed around an abstract `SyncProvider` protocol rather than hardcoding iCloud. iCloud is the first (and initially only) implementation, but the abstraction preserves room for future backends (Google Drive, Synology Drive, WebDAV, Dropbox) without redesigning the sync pipeline. GitHub is a separate, optional layer — not a `SyncProvider` implementation, but a version control + publishing bridge.

19. **TreeSitter for native code highlighting**: Native app uses TreeSitter for syntax highlighting in code blocks (via `WKWebView` or `AttributedString` rendering). Chosen over regex-based highlighters for accuracy and multi-language support. For the static site generator (publishing), we use Splash (Swift-native, for Swift code) and highlight.js (bundled JS, for all other languages) since TreeSitter requires native runtime.

20. **Embedding model distribution**: On-Demand Resources (ODR) for App Store builds (Apple-managed CDN, lazy download per model tier) + direct download from HuggingFace Hub for CLI / sideloaded builds (cached in `~/.maho/models/`). Models are HuggingFace safetensors format, loaded directly by `swift-embeddings` — no CoreML conversion needed. App prompts user before downloading; shows model size and expected quality improvement. This avoids bloating the app binary with multi-GB models while keeping the download UX smooth.

21. **Drop NLEmbedding, use `swift-embeddings`**: Apple NLEmbedding was originally planned as the zero-download "Built-in" tier for vector search. Tested on Mac mini M4 (macOS 26.3, 2026-03-05): **only English** is available for both word embeddings (300 dim) and sentence embeddings (512 dim). Japanese, Korean, Traditional Chinese, Simplified Chinese — all return `nil`. Apple Intelligence multilingual expansion (2025-11) covers Writing Tools (summarize/rewrite), not the NLEmbedding API. Decision: remove NLEmbedding entirely. Use [`jkrukowski/swift-embeddings`](https://github.com/jkrukowski/swift-embeddings) as the unified embedding runtime — pure Swift, runs HuggingFace models via MLTensor (macOS 15+ / iOS 18+), supports multilingual models (XLM-RoBERTa, BERT families). Default model: `all-MiniLM-L6-v2` (90MB, 384 dim, 50+ languages). Same author also maintains [`SQLiteVec`](https://github.com/jkrukowski/SQLiteVec), ensuring package compatibility.

22. **Heading-based chunking for embeddings**: Notes are split into chunks before embedding. Short notes (< 512 tokens) are embedded as a single chunk with title prepended. Long notes are split by markdown headings (`#`–`######`); each chunk is prefixed with the note title for context (`"{title}: {chunk_text}"`). No overlap (headings provide natural semantic boundaries). Frontmatter is not embedded (title/tags already indexed by FTS5). If a heading section exceeds 512 tokens, it is further split by paragraphs. Each chunk gets its own row in the vector index, with results aggregated to note level (best chunk score = note score).

23. **RRF hybrid search parameters**: Reciprocal Rank Fusion with k=60 (industry standard, used by Elasticsearch, Azure AI Search). Formula: `rrf_score = Σ 1/(60 + rank)` where rank is 1-based position. FTS5 and vector search contribute equally (1:1 weight). Each source returns top 50 results before fusion. Default search is FTS5-only; `--hybrid` flag enables RRF merge; `--semantic` flag uses vector-only. Graceful degradation: `--hybrid` without vector index falls back to FTS5 with a warning.

24. **Replace BGE-M3 with multilingual-e5-large**: Originally planned `BAAI/bge-m3` (1024 dim, ~2.2GB) as the Pro model tier. Discovered during implementation (2026-03-05) that BGE-M3 only ships `pytorch_model.bin` — no `model.safetensors`. `swift-embeddings` exclusively uses Safetensors format; no PyTorch loader available. Replaced with `intfloat/multilingual-e5-large` (1024 dim, ~2.2GB, XLMRoberta, safetensors ✅). Same model family as e5-small (both from intfloat), ensuring API compatibility. Quality is comparable to BGE-M3 on multilingual benchmarks.

25. **Slack-inspired UI layout**: Three-zone layout: A (vault rail, ~48pt) | B (tree navigator, ~240pt) | C (content). Vault rail uses rounded-square icons like Slack workspace switcher — one icon per vault, grouped by type (iCloud → GitHub → read-only), with `＋` at top to add vaults and author+settings pinned at bottom. B panel is a pure tree explorer (no mode switching) with sections: Starred collections → Collection tree (expand in-place to show notes) → Pinned notes → Recent. C panel has smart tab bar (hidden by default, appears only when editing a note and opening another — preserves unsaved state), breadcrumb navigation, and floating toolbar (minimal in view mode, expanded in edit mode). Search bar embedded in macOS title bar (like Slack), triggered by ⌘K, with scope picker (All Vaults / This Vault) and mode picker (Text / Semantic / Hybrid). Design goal: cleaner than Obsidian — no plugin ribbon, no permanent tab bar, no settings maze.

26. **Cloud Sync toggle + `device` vault type**: Added a per-device `sync.cloud` setting (`icloud` default, `off`) to support users who don't want or can't use iCloud. When OFF, vault registry (`vaults.yaml`) is stored locally (macOS: `~/.maho/vaults.yaml`, iOS: App Documents), and `type: icloud` vaults cannot be created. New `type: device` for app-managed local storage — path is platform-appropriate (macOS: `~/.maho/vaults/<name>/`, iOS: App Documents `vaults/<name>/`), works on all platforms regardless of Cloud Sync setting. Unlike `type: local` (macOS-only, user-specified path), `device` vaults work on iOS/iPadOS. Optional `github` field on `device` vaults enables backup via `mn sync`. Switching ON↔OFF migrates vault registry and offers to convert vault types (`icloud` ↔ `device` with file copy). Setting stored in UserDefaults (app) / `~/.maho/config.yaml` (CLI) — never in iCloud (chicken-and-egg). Onboarding flow asks "Enable iCloud Sync?" when iCloud is available; defaults to Cloud Sync OFF when iCloud is unavailable.

27. **`_index.md`-based ordering**: Replaced numeric file prefix ordering (`001-slug.md`, `002-slug.md`) with `_index.md` frontmatter-based ordering. Each directory's `_index.md` stores `order:` (note filenames) and `children:` (sub-directory names) fields that control display order. Rationale: (a) **iCloud-friendly** — reordering changes one file (`_index.md`) instead of renaming every file in the directory; (b) **clean filenames** — no `001-` noise in URLs, Git diffs, or external tools; (c) **graceful degradation** — files not listed in `order:` are appended alphabetically, so externally-created files appear automatically. Top-level collection ordering still uses `maho.yaml` `collections:` array. This also enables full drag & drop: notes can be dragged between collections, collections can be dragged into other collections, and sub-collections can be reordered — all backed by `_index.md` writes. Migration from numeric prefixes strips the `NNN-` prefix and populates `_index.md` with the correct order.

28. **NTHU Purple theme system (清華紫)**: Replaced the plain system-default color scheme (all-black dark / all-white light) with a custom purple theme inspired by NTHU's official school color. Centralized in a `MahoTheme` struct with static color properties for each zone. Color scheme:
    - **A column (VaultRailView)**: `#721F6D` (NTHU Plum purple) — same in both dark and light modes. All text/icons on A column use white for contrast.
    - **B column (NavigatorView)**: Dark mode `#4A1050` (deeper purple than A), Light mode `#E0CCE6` (muted lavender). Text adapts: white/light in dark mode, dark in light mode. Requires `.scrollContentBackground(.hidden)` on List to override sidebar material.
    - **C column (NoteContentView)**: Unchanged — system dark gray / white.
    - **Settings window**: Follows C column colors (system default). Bug fix: `preferredColorScheme` now applied to Settings scene (independent window wasn't inheriting from ContentView).
    - **Title bar**: Uses `.toolbarBackground` with A column color to match VaultRailView.
    - **System theme**: `appTheme` setting correctly switches all zones; "system" follows macOS appearance.
    - **Implementation**: `MahoTheme.swift` provides all colors as static computed properties reading `@Environment(\.colorScheme)` via a `MahoThemeColors` helper. Views reference `MahoTheme.vaultRailBackground`, `MahoTheme.navigatorBackground(for:)`, etc.

29. **VaultStore — unified data access layer**: All vault-related YAML/JSON persistence (registry, global config, vault config, device config) goes through a single `VaultStore` actor. Motivation: config read/write was scattered across 6+ files (`VaultRegistry.swift`, `Config.swift`, `Auth.swift`, `VaultInit.swift`, `Collection.swift`, `GitSync.swift`) with overlapping responsibilities, inconsistent path resolution, and no concurrency safety. `VaultStore` is the single entry point for: (a) registry load/save with proper iCloud → local → cache fallback, (b) path resolution (one function, not a free function), (c) typed config structs (`VaultConfig`, `DeviceConfig`, `GlobalConfig`) replacing `[String: Any]`, (d) cloud migration with cleanup. `VaultEntry.path` is only meaningful for `.local` type — ignored for `.icloud`/`.github`/`.device` (paths derived from name). See [vault-store.md](vault-store.md).

30. **Xcode 27 / iPhone 18 / iPhone Duo readiness** (2026-10-09): The project builds unchanged with Xcode 27.0 (iOS 27 / macOS 27 SDKs, Swift 6.4) and runs on the iPhone 18 Pro simulator; this entry records what the `feature/xcode27-iphone18-duo` branch changed and what is deliberately deferred.
    - **Main-actor `UIDevice`**: the iOS 27 SDK marks `UIDevice.current` as main-actor isolated. `currentDeviceName()` (Kit) and the app's `DeviceInfo` are now `@MainActor`; the free `mergeRegistries()` takes the device name as a required parameter and `VaultStore.mergeRegistries()` hops to the main actor to read it when the caller doesn't pass one. Same conflict-file naming as before.
    - **No screen-sized layout**: the editor's keyboard accessory toolbar no longer sizes itself from `UIScreen.main.bounds`. UIKit stretches an `inputAccessoryView` to the keyboard width, and on iPhone Duo (or iPad multitasking) the window is not the screen. There are no other `UIScreen` / idiom / orientation checks in the app — layout is size-class driven, so Duo's inner display (regular × regular) gets the iPad three-column UI via `AdaptiveIOSContentView` and the outer display (compact) gets the iPhone UI.
    - **Project spec**: `xcodeVersion: "27.0"`; iPhone orientations declared explicitly (portrait + both landscapes — Duo's "open, turned" pose is landscape) and `UIRequiresFullScreen: NO`. Together with the generated launch screen these are the keys App Store Connect's Duo resizability check looks at. Deployment targets stay macOS 15 / iOS 18; `ARCHS_STANDARD` still includes x86_64 because that only changes at a macOS 27 deployment target.
    - **Toolchain cleanups**: `git clone` subprocess code in `VaultInit` moved into one macOS-gated helper so the iOS build no longer reports "will never be executed" branches; a few unused-variable warnings removed. The intentional `searchNotes(query:)` substring fallback still trips its own deprecation warning.
    - **Verified at Duo's size classes on iOS 27.0 simulators** (2026-10-09): iPhone 18 Pro in landscape (874×402 pt, compact × compact — the classes Duo reports when closed and turned) renders the iPhone layout and floating toolbar correctly, which also confirms the newly declared landscape orientations take effect. iPad mini (A17 Pro) in portrait (744×1133) and landscape (1133×744), both regular × regular, bracket Duo's open window (871×669 on the 27.0 SDK, 951×669 on 27.1) and render the three-column iPad layout — the navigator overlays the detail at the narrow end and sits beside it at the wide end. The editor's keyboard toolbar was exercised on the iPhone 18 Pro after the `UIScreen.main` removal and fills the window width.
    - **Deferred until Xcode 27.1 ships**: the iPhone Duo simulator, Device Hub poses (Closed / Book / Open / turned), the trailing-edge vertical toolbar (`toolbarVerticalEdge`), reserved-region handling for the fold and cameras, and Duo App Store screenshots all require the iOS 27.1 SDK. That shipped as Xcode 27.1 RC (27A9275) on 2026-10-05 but is not installed on the build Mac; once it is, `scripts/verify-duo.sh` creates the Duo simulator, builds with that Xcode, installs, launches, and screenshots the outer and inner displays. With the 27.0 SDK the app fills most of Duo's inner display (≈871×669 pt, regular width) and the full outer display. Apple requires iOS 27 SDK builds and Duo screenshots for all submissions from April 2027.

31. **iPhone Duo support: full screen, trailing vertical bar, even split at the fold** (2026-11-09): Adopts the iOS 27.1 Duo APIs deferred in #30, for three poses — closed (outer display), open (inner display), and partially open (inner display folded like a book). The helpers live in `App/MahoNotes/DuoSupport.swift`; every use is behind `#available(iOS 27.1, *)` because the app deploys to iOS 18, and nothing changes on other devices.
    - **Full screen = 27.1+ SDK.** An app built with the iOS 27.0 SDK runs on Duo in a compatibility window that stops short of the status bar column, leaving an empty strip along the right edge of both displays (inner window 871 pt instead of 951). There is no Info.plist key for this; building with the iOS 27.1 SDK or later is the whole fix. Because the app now references 27.1 symbols (`toolbarVerticalEdge`, `reservedRegions`), it no longer compiles with the 27.0 SDK, so a release can't silently ship the letterboxed build. `project.yml`'s `xcodeVersion` is 27.2.
    - **Bottom controls move to the trailing vertical bar.** On Duo the system lays the status bar, navigation buttons, and toolbar items out vertically on the trailing edge (outer display always, inner display in landscape), but only for standard bars: a custom bar pinned to the bottom stays put. `ToolbarVerticalEdgeReader` reads `EnvironmentValues.toolbarVerticalEdge`; where it is non-nil, the iPhone layout hands its floating Liquid Glass toolbar's actions (New Note, New Collection, Sync Now, Settings) to a `ToolbarItemGroup(placement: .bottomBar)` instead of drawing the pill, and the iPad layout's detail column shows its navigation bar (which costs no height when vertical) with the view-mode toggle at `.topBarTrailing`. `FloatingToolbarView` hides its bottom-corner view-mode pill whenever a vertical bar exists, since both layouts put that toggle in the bar; the toggle takes over the pill's ⌘E. Everywhere bars stay horizontal (other iPhones, iPad, Duo's inner display in portrait) the reader reports `nil` and the existing floating UI is unchanged. Items use `Label` with existing localized titles so the overflow menu can list them.
    - **Even split when partially open.** HIG asks split views to even out their columns on the fold the way Notes does. Whether the device is folded like a book comes from two signals, either of which counts: the hinge (`onHingeChange`, wrapped as `onDuoHingeChange` → `DuoHinge.isBookFolded`) and the fold's `.division` reserved region turning active. Where the fold is comes from `onDuoFoldChange`, which reads the region with `.includeInactive` from a window-sized background and reports its center in global coordinates (falling back to the center of a landscape window if no region is reported, which is where the inner display's hinge runs when the app fills it). `FoldAlignedNavigatorWidth` then pins the navigator column to `min = ideal = max = fold − navigator leading edge`, so everything before the detail ends on the fold. The leading edge is measured rather than assumed, because the system may show or hide the vault rail on its own. On Duo the width modifier is applied in both states with only its values changing (flat: ideal 320, laid out at ≈341 pt), so folding never swaps the column's view identity and the navigator keeps its scroll position and expanded collections. `ArrangementView` was not used: it can't host a `NavigationSplitView`.
    - **Why the hinge, not just the region** (revised after TestFlight build 4, where half open looked the same as open on a real Duo): the `duo` log category on the simulator showed the hinge reporting `partiallyOpen` continuously from ≈125° to 175°, while the `.division` region stayed inactive throughout a 173° → 128° sweep and turned active only once the hinge stopped moving (Device Hub's own code talks of a device not earning the fold "until it settles"); geometry callbacks also only fire on relayout. A hand-held device never settles enough, so build 4, which waited for the region, never split. `partiallyOpen` spans nearly flat angles, so `isBookFolded` engages at ≤ 160° and releases above 170°; the 10° gap keeps a hand hovering near the threshold from flipping the layout.
    - **Inner display starts with navigator + note.** At 951 pt the split view won't tile rail + navigator + note while flat: it hid the rail on its own, and after a fold (where it does tile all three) it presented the rail as an overlay that dimmed the other columns. On the first hinge report `IPadContentView` therefore requests `.doubleColumn` (cycle state 1), the layout the system settles on anyway; folding then only moves the divider. The sidebar button still cycles the rail in, and the system may still show it while folded, which the measured leading edge accounts for.
    - **Search moves to the trailing vertical bar** on the inner display: HIG puts search at the trailing side of the toolbar for split-view apps that search across columns (Notes, Mail), and on Duo that toolbar is the vertical bar. The detail column gets `.searchable` while it has a vertical bar and the navigator gets it otherwise; both are attached from a `Color.clear` background, so moving search never changes either column's identity. Results still list in the navigator.
    - **Verified on the iPhone Duo simulator** (iOS 27.1 runtime, Xcode 27.2 27B52, SDK stamp 27.2): closed, the outer display is edge to edge with the four navigator actions in the vertical bar and a pushed note's back button + view-mode toggle there too; open, the inner display is 951×669 pt edge to edge with the toggle in the vertical bar and no pill; partially open, the navigator/detail divider lands at x = 475.7 pt against a 475.5 pt fold center, with the rail (0–68 pt) and navigator on the left half and the note on the right. Poses had to be switched by hand in Device Hub — see `scripts/verify-duo.sh`.
    - **Not changed**: Duo's tabletop pose (horizontal fold) gets the open layout; the navigator column's own controls (sidebar toggle, title, +) stay at the top of that column, as HIG's "locate controls near the content they affect" asks.
    - **Debugging on hardware**: `DuoSupport.swift` logs hinge status changes, fold measurements, and the navigator width it applies under subsystem `dev.pcca.maho-notes`, category `duo`. Stream them with Console.app (device attached) or, on the simulator, `xcrun simctl spawn <udid> log stream --level info --predicate 'category == "duo"'`. Make sure the simulator you look at has the current build: the stock "iPhone Duo" simulator kept an Oct 9 build while `verify-duo.sh` installs onto "Maho Duo Check".
32. **Curated vault color palette** (2026-11-09): Vault badges used SwiftUI system colors. A vault with no stored color got one of ten (`.yellow`, `.green`, `.cyan`, …) picked by a hash of its name, so most vaults showed saturated colors that clashed with the plum rail (#28). Even the explicit choices were mostly system colors.
    - **One palette, defined in the Kit.** `VaultColor.palette` (`Sources/MahoNotesKit/VaultColor.swift`) holds 24 colors as sRGB hex: three rows of hues and a row of muted tones, matching the six-column pickers. They come from one OKLCH family (lightness about 0.45–0.66, moderate chroma). Each keeps the white badge letter at ≥ 3:1 contrast (WCAG large text) and stays apart from the rail and from each other. `VaultColorTests` enforces all three. `MahoTheme` only converts these to SwiftUI `Color`.
    - **Names kept, values redrawn.** The registry stores the color name (`VaultEntry.color`). The 18 names older builds offered (`red` … `charcoal`) are still valid, now with theme-matched values, so existing choices change in place without rewriting data. An older build on another device still shows a similar system color. Six names are new: `forest`, `olive`, `orchid`, `berry`, `sand`, `mauve`.
    - **Every vault gets a stored color.** `VaultRegistry.addVault` gives an entry without a color the least-used palette color, breaking ties by `VaultColor.assignmentOrder`. That order alternates warm and cool and saves the colors closest to the rail for last. Every creation path goes through `addVault` (app, CLI, Getting Started, Find Missing Items), so new vaults get distinct colors until the palette runs out. On load, the app calls `VaultStore.assignMissingVaultColors()` once, which does the same for vaults registered before this change. Like the device-entry repair, it uses `loadRegistryForUpdate()` and saves only when a color was missing.
    - **Unknown names are left alone.** A name this build doesn't know may come from a newer build sharing the registry. It is never overwritten. It renders as a palette color derived from the vault name with FNV-1a, which is stable across launches and devices, unlike `hashValue`.

33. **GitHub sync reconciles three ways, merges collection indexes, never force-pushes** (2026-11-10, issue #2): Both GitHub sync paths treated a conflicting `_index.md` like a note (remote wins, local parked in a conflict copy), and the app's REST path had a larger problem found while auditing it.
    - **The REST path pushed first, with force.** `GitHubSyncManager.sync()` built a tree from the local files only, committed it on top of the remote head and force-updated the branch — before looking at what the remote had. A device with any local change therefore deleted the notes other devices had added since its last pull and reverted their edits (still in the Git history, gone from every device after the next pull). The conflict handling in `pull()` could not trigger: whenever local files had changed, the push had already overwritten the remote.
    - **Now: reconcile, then push without force.** Each file is compared three ways — the manifest (what both sides last agreed on), the local file, the remote file. A change on one side is taken, deletions included. A change on both sides keeps the remote version and saves the local one as a conflict copy; an edit beats a deletion in either direction. The push adds one commit on top of the head that was just reconciled with and is never forced: if another device pushed meanwhile, GitHub refuses the update and the cycle runs again (up to four times). A file saved locally while its remote version downloads also restarts the cycle instead of being overwritten.
    - **The two reasons push-first existed are handled differently.** (a) *Locally deleted files were re-downloaded*: with a three-way comparison a local deletion is a change like any other. (b) *A read right after a push could return the previous head*, and its tree would be taken for remote changes: the manifest records the parent of the last pushed commit (`lastPushParentSHA`, optional — older manifests load unchanged), and a head equal to it within two minutes of that push is treated as stale.
    - **`_index.md` merges by meaning** (`CollectionIndexMerge`, shared by both paths). Fields merge per key; `order:` and `children:` merge per entry against the common base: an entry either side removed stays removed (the lists are never simply united), additions from both sides are kept after the entry they followed, one side's reorder is kept, two different reorders are a conflict. No common base (first sync of two existing folders) means no merge. Anything undecidable falls back to the conflict-copy path. The CLI reads the base and both sides from the merge's index stages; the REST path fetches the base blob by the SHA in the manifest.
    - **"Synced" is not "resolved".** `SyncResult` gains `mergedFiles`, `unresolvedConflicts` (every conflict copy in the vault, including those from earlier syncs) and `status` (`ok` / `conflicts`). Exit codes are unchanged — existing automation that only checks for failure keeps working — and `mn skill` tells agents to read `status`. The app counts conflict copies from disk, so they are still reported after a relaunch.
    - **Conflict copies are device-local on both paths.** The REST path never uploaded them; the CLI committed and pushed them. Both now keep `*.conflict-*` in `.gitignore`. An `_index.conflict-*.md` is not listed as a note.
    - **Guards.** A vault folder that has lost its `maho.yaml` (a wiped container) is not pushed; a truncated tree listing is an error rather than "the rest was deleted"; `.git/` is never uploaded.
